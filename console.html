Designing for AI tools, with AI

HPDF Console

The High Performance Data Facility (HPDF) is a DOE user facility whose mission is o enable and accelerate scientific discovery by delivering data services at the scale. HPDF Console is a work in progress platform to allows facility users to access and work with data stored at HPDF.

Scientific data takes many forms, from simple CSV files to high volume data cubes. In my early explorations of the Console, I considered a common use case where scientists wants to be able to explore across two simple CSV files that don't share a common data model. I knew that I wanted to explore the interplay of data stored in a lakehouse and AI capabilities.


Early mockup shows that data files can be opened in tabs in the center panel. When AI generates a new file (such as merging two data files), that new file would be displayed as a new tab in the center panel.

Creating our design.md file

Separate from the main data platform, I was tasked to quickly design the onboarding and allocation request process. At this point, I decided to experiement with using AI to accelerate that process.

`design.md` files encode a product’s UX and visual design decisions in a format that both humans and AI can read, allowing agents to generate new screens that remain consistent with the rest of the product.

A common workflow for creating a design.md file is to provide an AI agent with an existing website and a design.md template, then prompt it to generate the file based on the site’s design. In my case, however, I had only a handful of early mockups rather than a live product. I uploaded these mockups as a starting point and, through a series of prompts, asked the AI to generate both a `design.md` file and an HTML prototype of the allocation request process.

Because the source material was limited, the AI had to make many design decisions on my behalf, and some of its initial choices weren’t ones I would have made. I iteratively reviewed and refined those decisions with the AI, using the evolving prototype to evaluate the design until I was satisfied with both the interface and the resulting design.md file.


Screenshot of the AI generated html prototype for reviewing allocation request submissions.

Defining screenflows for AI

Next, I needed to generate the onboarding process for new users. My initial experiment was to try uploading the journey map developed by our ux researcher, along with the design.md file. The first attempt produced a screen with a progress stepper, the first step labeled "See demonstrated value". This was obviously too literal of an interpretation of the journey map. But more than that, as I walked through the steps, I found that there were missing screens that I intuitively knew should be there.


I decided that a journey map wasn't at the right level of description for the AI and instead I mapped out the screens that I wanted. In the spirit of using a machine readable format, I encoded the flow in a mermaid diagram. The resulting flow produced by the AI was exactly what I wanted.
